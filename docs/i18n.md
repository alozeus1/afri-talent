# Frontend i18n

Locales: `en` (source of truth), `es`, `fr`, `pt`, `ar` (right-to-left).
Config: `frontend/src/lib/i18n/config.ts`.

## Where strings live

One folder per namespace, one file per locale:

```
frontend/src/lib/i18n/messages/
  define.ts              defineNamespace() - types every locale against en
  registry.ts            SITE_NAMESPACES + AREA_NAMESPACES (register new ones here)
  nav/      en.ts fr.ts es.ts pt.ts ar.ts index.ts
  auth/ common/ candidate/ pricing/ jobs/ home/ learning/
  interviews/ salaries/ companies/          -> merged into MESSAGES (useT)
  admin/                                    -> useAdminT  (admin-messages.ts)
  support/                                  -> useSupportT (support-messages.ts)
  employer/ employerJobs/ employerTalent/
  employerSetup/ employerInsights/          -> useEmployerI18n (employer-messages.ts)
```

The employer hook also exposes `ts(text)`, which translates English copy the
API still returns (onboarding checklist labels, trust badges, warnings, job
preview tips) by exact match against the `server.*` keys in
`messages/employer/en.ts`. Unknown text is shown unchanged, so keep those keys
in sync when backend copy changes.

Keys keep their full dotted name inside the file (`"nav.findJobs"`), so the
key you `grep` for is the key in the file. Every non-English file is typed
`satisfies Record<keyof typeof en, string>`: a missing or extra key is a
**compile error**, and `src/lib/i18n/__tests__/namespaces.test.ts` also checks
non-empty values and identical `{placeholders}` for every namespace and
locale.

Teams that own an area (employer, candidate, admin...) should add their own
namespace folder instead of growing a shared one. That way parallel work
never touches the same file.

## Adding a namespace

1. Copy an existing folder (for example `messages/nav/`) to `messages/<name>/`.
2. Put the English strings in `en.ts`, then translate every other locale file.
3. Register it in `messages/registry.ts`:
   - in `SITE_NAMESPACES` to make its keys available through `useT()`
     (key prefixes must be unique across site namespaces), or
   - in `AREA_NAMESPACES` and add a dedicated hook (see `support-messages.ts`)
     when the area wants its own key space and `{var}` interpolation.
4. Run `npm run i18n:check` and `npx jest src/lib/i18n`.

## Using translations in components

```tsx
"use client";
import { useT } from "@/lib/i18n/client";

export function Example() {
  const t = useT();
  return <h1>{t("nav.findJobs")}</h1>;
}
```

`useLocale()` resolves the active locale in this order:

1. a `/<locale>/...` path prefix (the `[locale]` routes),
2. the `afritalent-locale` cookie, which middleware sets on every localized
   visit and the language switcher sets on change,
3. `DEFAULT_LOCALE`.

So routes that live outside `[locale]`, such as `/employer/*` and `/admin/*`,
render in the user's chosen language with no extra wiring. Server rendering
has no cookie access in this hook (it uses `useSyncExternalStore` with a
`null` server snapshot), so the first paint is English and the client
re-renders with the cookie locale straight after hydration, with no hydration
mismatch. `<HtmlLangSync />` in the root layout keeps `<html lang dir>` in
sync on every route, so Arabic renders right-to-left everywhere.

Build links with `localizePath(href, locale)` so a user's language stays
attached to the URL.

## Checking coverage

```
npm run i18n:check                      # parity (fails) + hard-coded copy report
npm run i18n:check -- --area=employer   # one area only
npm run i18n:check -- --verbose         # every literal with file:line
npm run i18n:check -- --max-literals=N  # also fail above a budget (for CI ratchets)
```

The hard-coded copy report counts JSX text nodes and the `placeholder`,
`title`, `alt`, `aria-label` and `label` string attributes in `src/app` and
`src/components`, grouped by area. Move those strings into a namespace and
the count goes down. Brand names and code-like tokens may stay literal.
